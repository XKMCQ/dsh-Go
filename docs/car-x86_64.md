# x86_64 车机适配

面向：**能装普通 APK 的 x86_64 Android 车机**（后装安卓大屏、国产车机、Android-x86 车机）。
不是 Android Automotive OS 的 Car App 模板工程——那种要 CarAppService 和车厂白名单，本仓库没做。

一句话结论：仓库的 Dart、Gradle、运行时脚本**本来就带 x86_64 分支**，缺的是
「x86_64 运行时的构建渠道」和「车机那块又宽又矮的屏」两件事。本文给出包的办法和上车后的检查项。

---

## 1. 先判定：这台车机能不能跑

```bash
adb devices
python3 tooling/car_probe.py                  # 体检，只读，不改设备
python3 tooling/car_probe.py --serial <串号>
```

脚本按下面的硬门槛逐项判定，退出码 `0` 可装、`1` 装不上、`2` 有风险：

| 检查 | 门槛 | 不满足的后果 |
| --- | --- | --- |
| ABI | `ro.product.cpu.abilist` 含 `x86_64` | 只有 `x86` = **32 位 Android 系统**，x64 包直接装不上；本仓库没有 32 位运行时 |
| Android | API ≥ 26（minSdk） | 装不上 |
| Android | API > 28 时给提示 | 见 §6「私有目录 exec 限制」 |
| `/data` | 可用 ≥ 3 GB | 解开的 rootfs 约占 2 GB，太紧会解包失败 |
| 输入法 | `ime list -s` 非空 | 车内没键盘，没输入法就打不了字 |

> **32 位是最常见的坑。** Intel Atom 车机 CPU 是 x86_64，但装的 Android 可能是 32 位用户态，
> 此时 `abilist` 只有 `x86`。这种情况 x64 APK 连安装器都过不去，只能是另一条技术路线（见 §7）。

车机是 ARM（瑞芯微、全志等）的，用官方 arm64 包即可，不需要看本文。

## 3. 出包

`runtime/build-runtime.sh` 要在 **x86_64 Linux** 上跑：它要把打过补丁的引擎装起来跑自身的
构建步骤（pnpm / node / python 都是 Linux ELF）。Windows 上 Git Bash 不行，要么 WSL2，要么另一台 Linux 机器。

### 3.1 走 CI（推荐）

```bash
gh workflow run car-x64.yml --ref main
gh run watch
gh run download <run-id> -n car-x64-apk -D dist/car
```

产物：

- `runtime-x86_64`（artifact）：`runtime/out/x86_64`，可复用，重打 APK 不必再等运行时构建
- `car-x64-apk`（artifact）：`app-x64-release.apk` + `SHA256SUMS`

工作流做的事（与 `runtime.yml` 同一套哈希校验、同一个下载缓存）：

1. `runtime/build-runtime.sh x86_64` → `python3 -I tooling/check_runtime_bundle.py x64`
2. JDK 17 + Flutter `3.47.7` + NDK `28.2.13676358`（`runtime/tawcroot/source.json` 钉的版本）
3. `tooling/build-apk.sh -f x64 --no-companion -- --dart-define=DSH_CAR=1`

`--no-companion`：伙伴包是许可素材，不入库，车机包也不带。

### 3.2 本地 Linux 机器

仓库自带工具链安装脚本（JDK 17、Flutter 3.47.7、SDK、NDK，默认装到 `~/dev`，不需要 sudo）：

```bash
bash tooling/setup-toolchain.sh
source tooling/env.sh

runtime/build-runtime.sh x86_64
python3 -I tooling/check_runtime_bundle.py x64
(cd app && flutter pub get --enforce-lockfile)
tooling/build-apk.sh -f x64 --no-companion -- --dart-define=DSH_CAR=1
```

`--no-companion`：伙伴包是许可素材，不入库，车机包也不带。不带它就会去找
`~/keys/dsh-go/companion-pack-whale-girl.zip` 并失败。

APK 落在 `app/build/app/outputs/flutter-apk/app-x64-release.apk`。
已有 `runtime-x86_64` artifact 时，解到 `runtime/out/x86_64` 后可直接从第三条命令开始。
原生 Linux / macOS 都行；Windows 的 Git Bash 不行（JDK 与构建脚本取的都是 Linux/x86_64 二进制）。

签名：仓库外没有 `app/android/key.properties` 时，release 构建用 **debug key** 签名。
自己长期用就把 key.properties 配好（`storeFile`/`storePassword`/`keyAlias`/`keyPassword`），
否则换一次构建机就可能装不上（签名不一致要卸载重装，数据丢）。debug 签名的包也**替代不了**
官方 arm64 包的安装——两者签名不同，同机共存会打架。

## 4. 车载形态：`DSH_CAR`

| dart-define | 作用 |
| --- | --- |
| `DSH_CAR=1` | 布局按车机算：宽而矮的窗口不再降级成手机单列 |
| `DSH_CAR_LANDSCAPE=1` | 锁横屏。默认**不锁**——旋转屏车机（比亚迪类）一半时间是竖的，窗口类跟随系统 |

为什么需要 `DSH_CAR`：`app/lib/ui/shell/adaptive/adaptive_layout.dart` 里有一条规则
「高度 < 480dp 一律当横放手机处理」，理由是软键盘会吃掉下半屏。车机没有软键盘，
1280×480 在 240dpi 下是 853×320dp，按原规则会被判成 compact（抽屉式单列），
`DSH_CAR=1` 让它只看宽度：853dp ≥ 840 → expanded（常驻列表 + 右侧面板）。

预测某台车机会落到哪种布局：`python3 tooling/car_probe.py` 的「屏幕」一行会直接给出。

## 5. 安装与首次启动

三条路，按车机开放程度挑一条：

| 通道 | 做法 | 前提 |
| --- | --- | --- |
| USB ADB | `adb install -r app-x64-release.apk` | 车机有开发者选项、USB 调试，USB 口没被 CarPlay/投屏独占 |
| 无线 ADB | `adb connect <车机IP>:5555` 再 `adb install -r ...` | 车机与电脑同一 WiFi，且 ROM 开了 `adb tcpip 5555` |
| U 盘 / 文件管理器 | 把 APK 拷到 U 盘，车机文件管理器里点开安装 | 车机允许「未知来源」；部分 ROM 的文件管理器不认 apk 需换成第三方 |

装完启动：

```bash
adb shell am start -n io.github.ccch1mneyyy.dsh_app/.MainActivity
```

车机侧要放开的：

1. **未知来源安装**（`设置 → 应用 → 特殊权限 → 安装未知应用`）。
2. **电池/后台白名单**：车机 ROM 普遍激进杀后台。给 dsh-go 关掉省电限制，
   否则运行时会话被回收，下次打开要重新准备。
3. **首次启动要等**：运行时解包 + 准备约 1–3 分钟（x86_64 车机的 eMMC 比手机慢），
   期间界面是启动画面，属正常。装完第一次进「设置 → 关于/诊断」确认运行时版本已就绪。

> **别开「直接启动」。** 这个选项默认关闭，x86_64 上直跑 glibc 加载器会被部分系统的
> seccomp 过滤杀掉；默认的 PRoot 启动在 x86_64 上是稳的那条路。

## 6. 车机特有风险与处理

| 风险 | 症状 | 处理 |
| --- | --- | --- |
| 32 位用户态 | `adb install` 报 `INSTALL_FAILED_NO_MATCHING_ABIS` | 无解，需 32 位运行时（§7） |
| 私有目录 exec 限制 | 启动卡在「准备运行时」，日志里有 `Permission denied` / `exec` 失败 | targetSdk 28 已规避 Android 10+ 的整类限制；个别 ROM 另有策略，先把 App 装到内置存储（不是外置/TF 卡）再试，仍不行就带运行日志提 issue |
| 老 Atom / 精简指令集 | 启动即 `SIGILL`，日志有 `Illegal instruction` | `adb shell cat /proc/cpuinfo \| grep -m1 flags` 看有没有 `sse4_2 popcnt`；缺的话这台机器跑不了 Ubuntu 24.04 的用户态 |
| 无输入法 | 输入框点了没反应 | 车机应用商店装一个（讯飞/搜狗车机版），或用 `adb shell input text` |
| 语音输入无权限 | 点麦克风没反应 | 车机常把 `RECORD_AUDIO` 弹窗吞掉，去「应用权限」里手动给；没有麦克风的机型也能装（清单里已声明 `microphone` 非必需），只是语音用不了 |
| 悬浮桌宠不显示 | 开了没反应 | 需要「显示在其他应用上层」权限，车机 ROM 常把该权限藏起来 |
| 超宽屏两侧留白 | 内容居中、两边空 | 布局按 `contentWidth` 居中是有意为之，不是 bug |
| 伙伴小屋花屏 | 角色和背景布满细密横纹（约 8 行一个周期），Flutter 自己画的标题、气泡、输入条清晰，其他页面完全正常 | 见下方「渲染后端」说明，已由 x64 的 manifest 关闭 Impeller |
| 方向盘按键/旋钮 | 不能操作 | 未适配（§7） |

### 渲染后端：x86 车机关闭 Impeller

**症状**：伙伴小屋里角色和整块背景布满细密横向噪点，约 8 行一个周期；同一屏幕上
Flutter 画的标题、气泡、输入条、底部 tab 都清晰；退到对话列表等纯 Flutter 页面完全正常。

**取证**（`E371`，AMD Radeon renior + Mesa 23.2.1，Android 13）：

- `dumpsys SurfaceFlinger` 里伙伴小屋的 WebView 是 `SurfaceView[...](BLAST)`，
  `geomBufferSize=[0 0 2560 1600]`、`composition type=DEVICE`，即全屏 opaque 硬件叠加层。
- 截图做垂直自相关，`lag=8` 处峰值 0.87（8×8 正好是 AMD 的 micro-tile 尺寸），
  说明缓冲区被按错误的 tiling 解读。
- `logcat` 里该进程每帧一条 `FrameEvents: updateAcquireFence: Did not find frame`——
  合成器拿不到 acquire fence，会在 GPU 未画完时取走 buffer。
- 纯 Flutter 页面干净 → 排除 WebView 缓冲区损坏、也排除 HWC 整体读错。

**结论**：Impeller 的 Vulkan 后端（RADV）与全屏 SurfaceView 的 WebGL 页在同一帧合成时
缺同步。把页面改成 TextureView 单独试过，**无效**；关掉 Impeller 后噪点消失，
`edge` 指标从 35–46 降到 4–8（纯色/渐变区间的正常值）。

**落地**：`app/android/app/src/x64/AndroidManifest.xml` 里
`io.flutter.embedding.android.EnableImpeller = false`。这是 x64 flavor 专属的 overlay，
`arm64` 与手机版仍走 Impeller。改完用 `aapt dump xmltree ... AndroidManifest.xml` 确认
meta-data 已进包。

**若将来 Mesa 或 Impeller 修好想恢复**：删掉那个 overlay 文件即可，然后用伙伴小屋
复验——只看一句话：背景还有没有横纹。

## 7. 明确没做的适配

写清楚边界，免得后面当成 bug：

1. **32 位（x86 / armeabi-v7a）运行时**：没有构建路径，也没有 flavor。要做得先解决
   32 位 Node/CPython 与 proot 的整套依赖，工作量在运行时侧，不在 UI 侧。
2. **Android Automotive OS 的 Car App 模板**（`CarAppService` + `car-app-library`）：
   那是车厂白名单 + 模板渲染的模型，和本 App 自绘 UI 的形态冲突。
3. **方向盘按键 / 旋钮焦点导航**：Flutter 的焦点系统能接，但没有为车机做过焦点顺序与
   大焦点框的设计，现在只能触摸。
4. **行车限制（driving restriction）**：没有按车速禁用交互的逻辑。
5. **车机 Launcher 卡片 / 负一屏小组件**：没有。

验证过的（本机 Windows，Flutter 3.47.7 + Android SDK 36，Maven/Gradle 走腾讯云与阿里云镜像）：

| 命令 | 结果 |
| --- | --- |
| `(cd app && flutter analyze --no-pub)` | `No issues found!`（82.7s） |
| `(cd app && flutter test test/shell/adaptive/adaptive_layout_test.dart)` | 27 个用例全过，含新增的 2 个车机用例 |

| `flutter build apk --debug --flavor x64 --dart-define=DSH_CAR=1` | 成功，`app-x64-debug.apk` 155 MB；`aapt2 dump badging` 显示 `native-code: 'x86_64'`，`touchscreen`/`telephony`/`microphone` 三项均为 `uses-feature-not-required` |
| `tooling/build-apk.sh -f x64 --no-companion --dry-run -- --dart-define=DSH_CAR=1` | 命令拼装正确，`DSH_CAR=1` 确实进到 flutter |
| `python3 tooling/car_probe.py --props <x86_64 / 32 位 x86 / ARM 三种样本>` | 判定与退出码 0/2/1 符合预期 |

**没验证的**：x86_64 运行时构建与 release APK（本机是 Windows，`runtime/build-runtime.sh` 需要 Linux 主机）；
真机装车、车机 ROM 的后台策略、方控与语音。这些只能在 `car-x64.yml` 跑通后、拿真车机验。

编译顺带产出的 `app-x64-debug.apk` 是 **debug、不带运行时** 的包：引擎起不来，但界面和
`DSH_CAR` 布局能看。装到车机上先确认大屏布局和触控尺寸，再去做运行时那一半，能省一轮。
